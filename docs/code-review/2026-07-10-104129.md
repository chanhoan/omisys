### HIGH

#### H1. `updateUserRole` 요청/응답 role 직렬화 비대칭 → 관리자 UI에서 항상 400 가능성
**파일**: `service/user/server/src/main/java/com/omisys/user/domain/model/vo/UserRole.java` (`@JsonCreator fromString`, `@JsonValue getRole`)
**연관**: `UserController.updateUserRole` (신규), `UserRequest.UpdateRole` (신규), `UserResponse` L29 (`.role(user.getRole().name())`)

`UserRole`은 `@JsonValue`/`@JsonCreator`가 **한글 라벨**("관리자"/"매니저"/"사용자")을 기준으로 동작한다. 반면 조회 응답(`UserResponse`)은 `getRole().name()`으로 **enum name**("ROLE_ADMIN")을 내려준다. 새 `PATCH /api/users/{userId}/role`은 `@RequestBody UserRequest.UpdateRole { UserRole role }`을 역직렬화하므로, 프론트가 조회 응답에서 받은 `"ROLE_ADMIN"`을 그대로 재전송하면 `fromString`이 `null`을 반환하고 `@NotNull`에 걸려 **400**이 된다. `"관리자"`를 보내야만 동작한다.

**실증** (컴파일된 클래스 + Jackson 2.15.4로 직접 확인):
```
serialize(ROLE_ADMIN)             = "관리자"
deserialize {"role":"ROLE_ADMIN"} -> null
deserialize {"role":"관리자"}      -> ROLE_ADMIN
```

**재현 시나리오**: 관리자 콘솔이 사용자 목록(GET)에서 `role="ROLE_ADMIN"`을 받아 권한 변경 드롭다운을 구성 → 선택값 `"ROLE_MANAGER"`를 PATCH body로 전송 → `fromString`이 라벨 매칭 실패로 null → 검증 실패 400. 승격 기능이 동작하지 않는다.

**부가 문제**: `fromString`이 미매칭 시 예외가 아니라 `null`을 조용히 반환(silent failure)하여, 원인이 "권한 비어 있음"으로 오도된다.

**권장 수정 (택1)**
- 요청 계약을 name 기반으로 통일: `UpdateRole.role`을 `String`으로 받아 서비스에서 `UserRole.valueOf(...)`로 변환하고 실패 시 명시적 도메인 예외. (응답도 이미 name이므로 대칭이 맞음)
- 또는 enum의 `@JsonValue`/`@JsonCreator`를 name 기반으로 정렬. 단, 이는 `UserRole`을 직렬화하는 다른 경로(JWT claim 등) 전반에 영향이 있으므로 파급 검토 필요.

### MEDIUM

#### M1. springdoc-openapi 의존성만 추가되고 문서 노출 경로가 미완결
**파일**: `service/{delivery,review,search,notification}/server/build.gradle` (+springdoc), 각 서비스 `SecurityConfig`

`springdoc-openapi-starter-webmvc-ui:2.6.0`를 delivery·review·search·notification에 추가했으나:
- **delivery / review / notification**: `SecurityConfig`에 `/v3/api-docs/**`, `/swagger-ui/**` permitAll 화이트리스트가 없어 `anyRequest().authenticated()`에 걸린다. (product·order·user는 이미 보유 — 일관성 결여)
- **search**: `SecurityConfig` 자체가 없다.
- **gateway**: `gateway.yml`에 swagger 라우트가 없다.

결과적으로 게이트웨이 경유로도, 직접 접근으로도(다운스트림이 `X-User-Claims` 부재 시 차단) Swagger UI에 도달하기 어려워 **추가 목적(문서 노출)이 달성되지 않을** 가능성이 높다. 보안상 유해하진 않으나 변경이 미완결이다.

**권장**: 이미 화이트리스트를 가진 서비스와 동일하게 4개 서비스의 `SecurityConfig`에 api-docs/swagger-ui permitAll을 추가하거나(직접 접근 문서화), 게이트웨이에 문서 라우트를 두어 의도를 명확히 한다. 문서 노출이 당장 필요 없다면 의존성 추가를 되돌린다.

#### M2. `getAllOrder`의 fetchJoin + 페이지네이션 — 인메모리 페이징 경고 (기존 이슈, 확대됨)
**파일**: `OrderRepositoryImpl.getAllOrder` L56–61

`order.orderProducts` 컬렉션을 `fetchJoin()`한 상태에서 `offset/limit`을 적용하면 Hibernate가 DB 페이징 대신 전체 fetch 후 메모리 페이징(HHH000104)을 수행할 수 있어 대량 주문에서 정확도·성능 문제가 생긴다. 이 변경이 새로 만든 문제는 아니고 기존 `getMyOrder`와 동일 패턴이나, 관리자 전체 조회(필터 확장)로 데이터량이 커지는 경로라 영향이 크다.

**권장**: ID 페이징(2-step) 또는 `@BatchSize`/별도 카운트 전략 검토. 본 PR 범위 밖이면 후속 이슈로 기록.

## 잘 처리된 부분 (GOOD)

- **권한 상승 차단**: `createUser`가 요청의 role을 무시하고 `UserRole.ROLE_USER`를 강제 + `UserRequest.Create`에서 role 필드 제거 + 회귀 테스트(`createUser_alwaysForcesRoleUser`) 추가. 핵심 보안 개선.
- **게이트웨이 preflight bypass**: `CorsUtils.isPreFlightRequest` 통과 처리 + "게이트웨이 단독으로 인증 보장 아님, 다운스트림 defense-in-depth 의존" 주석이 정확하다. `SecurityContextFilter`가 `X-User-Claims` 부재 시 인증을 세우지 않아 `anyRequest().authenticated()`로 차단되는 구조와 일치.
- **시드 SQL**: `:BCRYPT_HASH` 플레이스홀더 + README 치환 지시 + 커밋에 실제 비밀 없음. `INSERT ... SELECT ... WHERE NOT EXISTS`로 idempotent. `role='ROLE_ADMIN'`은 `@Enumerated(EnumType.STRING)`(enum name 저장)과 정합, tier `'아이언'`도 정합.
- **invoice 정본 정리**: order의 `PATCH /invoice-number`를 `@Deprecated` + Javadoc으로 명시하고 delivery `/invoice`를 정본으로 문서화 — 계약 혼선 방지.
- **`hasRole('ROLE_ADMIN')`**: Spring의 `getRoleWithDefaultPrefix`가 `startsWith(rolePrefix)` 체크를 하므로 이중 접두사가 발생하지 않는다. 정상 동작(기존 `hasAnyRole` 컨벤션과 동일).
- **테스트**: order 3건(state 변환/오류/하위호환), user 3건(role 강제/승격/미존재) 신규 추가 — 변경 표면을 잘 덮는다.

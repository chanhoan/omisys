### MEDIUM

#### M1. `springdoc` 의존성만 추가되고 문서 노출이 부분적으로 미완결
**파일**: `service/{delivery,notification,review,search}/server/build.gradle`, 각 `SecurityConfig`

- **delivery / notification / review**: 이번 PR에서 `/v3/api-docs/**`, `/swagger-ui/**` permitAll 화이트리스트를 추가해 정상적으로 완결됐다(product/order/user 패턴과 일치). 세 서비스 모두 `starter-security`가 classpath에 있으므로 화이트리스트가 실질적 의미를 갖는다. **적절함.**
- **search**: `springdoc` 의존성을 추가했으나 **`SecurityConfig`도, `spring-security`(starter-security)도 존재하지 않는다**(확인함). PR 본문도 이를 "out of scope"로 명시한다. 이 경우 Spring Security가 요청을 가로막지는 않으므로 `/swagger-ui.html`이 오히려 접근 가능할 수 있으나, 그렇다면 인증·게이트웨이 보호 없이 문서가 노출되는 셈이다. 보안 관점에서 **search의 인증 부재 자체가 별도 확인 대상**이다.

**권장**: search에 대해 (a) SecurityConfig를 추가해 문서 노출 범위를 명시적으로 통제하거나 (b) 인증이 게이트웨이에서만 처리되는 게 의도인지 확인. 최소한 후속 이슈로 트래킹. 본 PR 범위 밖이라는 판단에는 동의하나, "search에 인증 계층이 없다"는 사실은 기록해 둘 가치가 있다.

#### M2. `getAllOrder`의 `fetchJoin` + 페이지네이션 — 인메모리 페이징 위험 (기존 패턴, 관리자 경로로 확대)
**파일**: `OrderRepositoryImpl.getAllOrder` (fetchJoin + offset/limit)

`order.orderProducts` 컬렉션을 `fetchJoin()`한 채 `offset/limit`을 적용하면 Hibernate가 DB 페이징 대신 전체 로드 후 메모리 페이징(HHH000104)을 할 수 있다. 기존 `getMyOrder`와 동일 패턴이라 이 PR이 새로 만든 문제는 아니나, state/date 필터 확장으로 관리자 전체 조회량이 커질 수 있어 영향이 커진다.

**권장**: 후속으로 2-step ID 페이징 또는 `@BatchSize` 검토. 본 PR에서 즉시 고칠 항목은 아님.

### LOW

#### L1. 에러 코드 HTTP 상태 불일치 — `ORDER_STATE_NOT_FOUND`가 잘못된 입력에 404
**파일**: `OrderErrorCode.ORDER_STATE_NOT_FOUND(HttpStatus.NOT_FOUND, ...)`, `OrderService.getAllOrder`

잘못된 `state` 쿼리 파라미터(예: `?state=XXX`)는 클라이언트 입력 오류이므로 `400 Bad Request`가 적절한데 `404 NOT_FOUND`를 반환한다. 대비되게, 이 PR에서 새로 추가한 `UserErrorCode.ROLE_INVALID`는 동일 성격의 문제에 올바르게 `400`을 쓴다 — 같은 "잘못된 enum 문자열" 상황을 두 서비스가 다르게 처리한다. `ORDER_STATE_NOT_FOUND`는 기존 코드라 이 PR의 신규 결함은 아니나, 새 필터가 이 코드를 재사용하므로 표면화된다.

**권장**: 잘못된 필터 입력에는 `400` 계열 에러 코드 사용을 검토(별도 `ORDER_STATE_INVALID` 등). 우선순위는 낮음.

#### L2. `from`/`to` 경계 및 유효성 미검증
**파일**: `OrderController.getAllOrder`, `OrderRepositoryImpl`

`from > to`인 역전 범위를 보내도 검증 없이 빈 결과를 반환한다. `createdAt.goe(from)`/`loe(to)`는 `LocalDateTime` 기준이라 컨트롤러가 ISO DATE_TIME을 요구하므로 자정 경계 이슈는 없다. 잘못된 형식은 Spring이 400으로 처리하므로 큰 문제는 아니나, 역전 범위에 대한 명시적 검증이 있으면 사용성이 낫다. 선택 사항.

## 잘 처리된 부분 (GOOD)

- **권한 상승 차단(핵심)**: `createUser`가 요청 role을 무시하고 `UserRole.ROLE_USER` 강제, `UserRequest.Create`에서 role 필드 제거, `createUser_alwaysForcesRoleUser` 회귀 테스트. 이 PR의 가장 중요한 보안 수정.
- **admin 전용 role 변경**: `@PreAuthorize("hasRole('ROLE_ADMIN')")` + `String`→`valueOf`→`ROLE_INVALID` 검증. `hasRole('ROLE_ADMIN')`은 Spring의 `getRoleWithDefaultPrefix`가 `startsWith` 체크를 하므로 이중 접두사 없이 정상 동작.
- **게이트웨이 preflight bypass**: `CorsUtils.isPreFlightRequest` 통과 + "게이트웨이 단독 인증 보장 아님, 다운스트림 defense-in-depth 의존" 주석이 실제 구조(`SecurityContextFilter`가 `X-User-Claims` 부재 시 인증 미수립 → `anyRequest().authenticated()` 차단)와 정확히 일치.
- **시드 SQL**: `:BCRYPT_HASH` 플레이스홀더 + README 치환 지시 + 커밋에 실제 비밀 없음, `INSERT ... WHERE NOT EXISTS`로 idempotent, `role='ROLE_ADMIN'`(`@Enumerated(EnumType.STRING)`과 정합)·tier `'아이언'` 정합.
- **invoice 정본 정리**: order `PATCH /invoice-number`를 `@Deprecated`+Javadoc으로, delivery `/invoice`를 정본으로 명시.
- **테스트 커버리지**: order 3건, user 4건 신규. 하위호환·오류 경로·보안 불변식을 모두 덮음.
